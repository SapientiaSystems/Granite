# Granite.Web

## Overview

React 19 and TypeScript single-page app, built as yarn components published to npmjs (`Components/*`, dist-tag `snapshot-1.0.0`) and assembled by the Vite `Applications/Granite.Web.AppHost`. Tests are Vitest with jsdom and Testing Library.

## Commands (from `FrontEnds/Granite.Web`, or the root `build-granite-web`)

- `yarn run test-granite-web`: all test projects; `test-granite-web-authentication`, `test-granite-web-user`, `test-granite-web-client`, `test-granite-web-session`, `test-granite-web-feedback`, `test-granite-web-survey`, `test-granite-web-content`, `test-granite-web-agent`, `test-granite-web-account` and `test-granite-web-navigator` run one. Each publishes its component to npmjs, then runs Vitest in `Tests/Granite.Web.<Component>Test`.
- Test layout: `Tests/Granite.Web.<Component>Test/src/test/typescript/<Subject>Test.ts(x)` (private projects, never published, importing subpaths such as `granite.web.authentication/Authentication`). Export from the component's `index.ts` whatever a test needs. Header name is the test project, for example `Granite.Web.AuthenticationTest`.
- `yarn run build-granite-web-<component>` and `yarn run build`: type-check, bump the snapshot version in each component's `src/main/typescript/package.json`, publish to npmjs under dist-tag `snapshot-1.0.0`, and wait until the new version is visible (`await-published.js`). `dist/**` under the AppHost is build output and is not committed.
- `containerize-*` and `push-*` publish images, tagged `<version>-<yyyyMMddHHmmss>-<local|dev>` from `BUILD_IMAGE_TAG` (no `latest`) by `docker-image.js` and skipped when `BUILD_IMAGE_TAG` is unset (`DOCKER_IMAGE_DRY_RUN=1` prints the command; see `Shared/Granite.Kubernetes/IMAGE-TAGGING.md`) (AppHost and ClientHost: `containerize-granite-web-clienthost`, `push-granite-web-clienthost`, `build-granite-web-clienthost`): never run them without approval. ClientHost (`Applications/Granite.Web.ClientHost`, image `granite-web-clienthost`, dev port 5174, `config.js.template` with `application: "client"`) is the ClientAdmin app: an `AppShell` frame like the AppHost `MenuBar` (56 px header, `padding="md"`, a Clients tab, burger navbar on mobile) with `PreferencesProvider`, routes login, login/callback, `clients` showing `OwnedClientsView` (toolbar Refresh and Rotate Secret; `/` redirects there) and `preferences` (`PreferencesView`, linked from the `UserMenu`; the Clients tab leads back). Both apps start with `defaultColorScheme="dark"`.

## Style

- `//////` header with the component name and a `//////` footer in every source file; no explanatory comments.
- `Array<T>`, never `T[]`. Allman braces. Call arguments as `(a,b)` with no space after commas. Aligned imports and declarations.
- Each component's `src/main/typescript/package.json` declares the dependencies the published package needs; the component's `package.json` declares the dev and build ones. Keep both in step.

## Authentication (`Granite.Web.Authentication`)

The browser holds no tokens. It carries the HttpOnly cookies `__Host-<PREFIX>_SID` and `__Host-<PREFIX>_DID` (set by the Gateway and the FrontEndController) and the script-readable `__Host-<PREFIX>-XSRF-TOKEN`; `<PREFIX>` is `cookiePrefix` from `window.__GRANITE_CONFIG__` (env `COOKIE_PREFIX`, default `GRANITE`, `[A-Z0-9_]+`, else the default). The Gateway swaps the cookie for a JWT, so the SPA never sends `Authorization` and never uses `localStorage` or `sessionStorage` for session data.

- `Http/`: `CsrfFetch` adds `X-XSRF-TOKEN` (raw cookie `csrfCookieName(prefix)`) to POST, PUT, PATCH and DELETE and retries once after a 403 when the cookie changed. `SessionFetch` retries once after a 401 when its handler (the manager) says the session is valid again. The typed FEC client (`GraniteFrontEndControllerServiceClient` from `granite.frontendcontroller.client`, one client for the Users, Session and Preferences operations) takes an optional fetch function, and Authentication passes these layers to them; they reject non-200/500 responses with a Strata `ServiceError`.
- `Authentication/`: `ISessionService` and `FrontEndSessionService` call `getSessionOutput` and `handleSessionInput` on a `GraniteFrontEndControllerServiceClient` (`/get-session-output`, `/handle-session-input`) with the flat `SessionInput` and `SessionOutput`, keyed by `Session.New->LoginView`, `Session.New->{Login,StartOktaLogin,CompleteOktaLogin}->LoginView`, `Session.Current->SessionView`, `Session.Current->Logout->LoginView` and `Session.Current->ChangePassword->ChangePasswordView`; no `userId` placeholder is sent. `AuthenticationManager` holds the state (`restoring`, `anonymous`, `authenticated`, `reauthenticating`; no tokens), exposes login, Okta start and completion (only a local `returnTo` is honoured), logout (closes only this application session; the Okta session is never ended), `changePassword` (`ISessionService.changePassword` returning `IChangePasswordResult`; `useAuthentication().changePassword`) and `handleUnauthorized`. State also carries `passwordEnabled` and `passwordSet` from `SessionOutput`.
- 401 flow: the app clients (`useAuthentication().createFrontEndClient((url,fetchFunction) => new XClient(url,fetchFunction),service)`, a typed factory over the session fetch) report a 401 to `handleUnauthorized`, which asks `Session.Current->SessionView`. AUTHENTICATED (for example another tab logged in again): the request is retried once. Otherwise the status becomes `reauthenticating`, `ReauthenticationDialog` opens over the page (password form and/or Okta with the current path as `returnTo`) and the request is retried once after login. Cancelling fails the request and logs the SPA out locally. Concurrent 401s share one prompt. The session service itself uses plain `CsrfFetch`, so the start-up `SessionView` 401 is not a re-authentication event.
- `Login/`: `LoginForm` shows only the methods enabled in the `passwordEnabled` and `oktaEnabled` flags of `SessionOutput`; `LoginView`; `LoginCallbackView` (the `/login/callback` route, `code`, `state` and `error` from the query); `ReauthenticationDialog` (rendered by `AuthenticationProvider`); `ChangePasswordDialog({ opened, onClose })` (current, new and confirm password; shows the policy failure messages); `UserMenu({ preferencesPath?, loginPath?, items?, className?, style? })`, the app-bar user menu (user name or "Login"; items in this order: Login (navigates to `loginPath`, default `/login`) or Logout (then navigates to `loginPath`), Change Password (opens `ChangePasswordDialog`; only when password login is enabled and the user has a password), Preferences when a path is given, then extra `items`). Navigator's `MenuBar` uses it with `preferencesPath="/user"`.
- `createAuthentication(options)` wires the fetch layers, the session service and the manager; tests pass a fake FEC client, a fake `fetch`, a cookie reader and a navigator. `SessionOutput` carries no user id, so the Users screen finds the caller by `userName` among the loaded users.
- Runtime config is `window.__GRANITE_CONFIG__.apiBaseUrl` only (nginx `config.js`); there is no Google client id.

## Navigator and AppHost

`UsersView({ service?, height?, className?, style? })` lives in `Granite.Web.User` (subpath `granite.web.user/Users`, default service `frontendcontroller-user-service`; `Granite.Web.User` depends on `granite.web.authentication`, so build order is authentication, user, client, session, feedback, survey, content, agent, account, navigator). It passes the `output.roles` catalog to `UsersEditableView` (`roles` prop), whose authorities cell editor is a Mantine `MultiSelect` pick list of that catalog; `RoleCascade.ts` (`selectRole`, `deselectRole`, `removeRole`, `applySelection`, `roleOptions`) applies the hierarchy cascade, including on chip removal. It creates `GraniteFrontEndControllerServiceClient` instances with `createFrontEndClient((url,fetchFunction) => new GraniteFrontEndControllerServiceClient(url,fetchFunction),"frontendcontroller-user-service")` and calls `getUsersOutput` and `handleUsersInput`. `SessionsView({ service?, height?, className?, style? })` lives in `Granite.Web.Session` (subpath `granite.web.session/Sessions`; `granite.web.session/View` exports `SessionsGrid`, `SessionValuesDetail` and the pure helpers in `SessionRows.ts` used by `Granite.Web.SessionTest`). It calls `getSessionsOutput` with source `Session.Open` (or `Session.All` when the toolbar switch Include closed is on) and `handleSessionsInput` with command `Close` and `sessionIdsToClose`. The read-only AG Grid shows `SessionRowData` rows (user name or `#id`, authorities, device, login method, created, last activity, expires, closed reason, replaced by, copied from) with an expandable read-only values row. The End button shows only for `canEdit(state)` and is disabled when no open session is selected or the selection includes `currentSessionId` from the output (the FEC refuses it too); a confirmation modal lists the sessions first. The AppHost routes `sessions` and Navigator's `MenuBar` has a Sessions tab. `Granite.Web.Client` (`granite.web.client/Clients`, `granite.web.client/Owned`): `ClientsView` is the admin grid of API Clients (`getClientsOutput`/`handleClientsInput`, source `Client.All`, destination `ClientsEditableView`, commands `Save`, `Delete`, `Rotate`; one new Client per Save; Add, Edit, Save and Undo work as in the Users grid, and Rotate Secret is disabled while editing) and `OwnedClientsView` the ClientAdmin grid (`getOwnedClientsOutput`, `handleOwnedClientSecretInput` command `Rotate`), used by ClientHost. A new or rotated secret appears only in `SecretDialog` state (cleared on close, never stored or logged; Download .env uses a Blob URL that is revoked about 1 s after the click, via `setTimeout`). The `.env` file (`toEnvFile`) holds `<envPrefix>-client-name`, `<envPrefix>-client-id` and `<envPrefix>-client-secret`; `ClientsView` and `OwnedClientsView` take `envPrefix` (default `granite`, `DEFAULT_ENV_PREFIX`; letters, digits, `.`, `_` and `-` only, `isValidEnvPrefix`) and pass it to `SecretDialog`. It reuses the authorities editor and `RoleCascade` of `granite.web.user/EditableView` and never offers `ROLE_ADMIN`. `granite.web.authentication` exports `APPLICATION` (`window.__GRANITE_CONFIG__.application`, default `granite`) and sends it as `application` with the password login and Okta start. The AppHost routes `clients`; Navigator's Clients tab shows for `ROLE_ADMIN`, `ROLE_AUDITOR` or `SCOPE_internal` (`IMenuTab.authorities`). `Tests/Granite.Web.ClientTest` covers the helpers. `Granite.Web.Feedback` (`granite.web.feedback/Feedback`, `granite.web.feedback/Review`): `FeedbackView` submits `handleFeedbackInput` (`Feedback.New->Submit->FeedbackView`, `{type, summary, details}`; the type-specific fields and validation live in `FeedbackForm.ts`) and is the Navigator HelpView's Provide Feedback section; `FeedbackReviewView` loads `getFeedbackReviewOutput` (`Feedback.All->FeedbackReviewView`) and saves `handleFeedbackReviewInput` (`Feedback.All->Save->FeedbackReviewView`, the changed rows from `changedFeedback`), with status and notes editable for `canEdit(state)`. The AppHost routes `feedback` to the review grid and `MenuBar` has a Feedback tab; `Tests/Granite.Web.FeedbackTest` covers the pure helpers. `Granite.Web.Survey` (`granite.web.survey/Survey`, `granite.web.survey/Review`): `SurveyView` loads the questions with `getSurveyOutput` (`Survey.New->SurveyView`) and submits `handleSurveyInput` (`Survey.New->Submit->SurveyView`, `{answers, comment}`; helpers in `SurveyForm.ts`) and is HelpView's Take Survey section (Dismiss returns to Search Help); `SurveyReviewView` loads `getSurveyReviewOutput` (`Survey.All->SurveyReviewView`), shows one column per question and the averages, and saves `handleSurveyReviewInput` (`Survey.All->Save->SurveyReviewView`, rows from `changedResponses`). The AppHost routes `surveys` to it and `MenuBar` has a Surveys tab; `Tests/Granite.Web.SurveyTest` covers the helpers. `Granite.Web.Content` (`granite.web.content/Search`, `granite.web.content/Markdown`): `ContentSearchView` is HelpView's Search Help: it loads the topic index with `getContentOutput` (`Content.All->ContentView`), searches with `handleContentInput` (`Content.All->Search->ContentView`, debounced 300 ms, at least 2 characters) and opens an article with `Content.All->Open->ContentView` (`articleKey`); history (`ContentHistory.ts`) drives back/forward; `MarkdownView` renders the body and turns `content:<key>` links into in-view navigation (external `http(s)` links open in a new tab; nothing else is a link, and raw HTML is never rendered). `Tests/Granite.Web.ContentTest` covers the parser and history. `Granite.Web.Agent` (`granite.web.agent/Chat`; single folder, so it has `Unused/index.ts`): `AgentChatView` is HelpView's Chat With Virtual Assistant: `getAgentOutput` (`Agent.Current->AgentView`) loads the latest conversation; `handleAgentInput` sends `Agent.Current->Send->AgentView` (`{conversationId, text}`), `Approve` and `Decline` (`{conversationId, toolUseId}`) for a pending action card; tool steps show as dimmed one-line entries and assistant replies render with `MarkdownView` (depends on `granite.web.content`). `Tests/Granite.Web.AgentTest` covers the helpers in `AgentChat.ts`. `HomeView({ service? })` (`granite.web.navigator/Home`) is the dashboard: once the session is authenticated it calls `getHomeOutput` (`Home.Current->HomeView`) and shows a toolbar with the user name, role badges (`output.roles`, else derived from `state.authorities`), the date and the as-of time; a top row of subject panels (Users, Sessions, Feedback, Surveys: headline number, 7-day sparkline, split bar, two facts); then logins per day for 14 days by login method, how sessions started in the last 7 days ended, feedback by type and status, and the survey averages. A section whose read failed shows Unavailable and the failure messages appear in an alert; a 403 (callers outside the Gateway users readers) shows a no-access note, and an anonymous visitor a log-in note. The pure helpers live in `HomeDashboard.ts`; `Tests/Granite.Web.NavigatorTest` covers them.  The AppHost routes `login` and `login/callback`; the Okta redirect URI configured in Session must be the SPA's `/login/callback`.

## Preferences (`Granite.Web.Account`)

`PreferencesProvider` (mounted by the AppHost inside `AuthenticationProvider`; applications can mount it too) loads `getPreferencesOutput` (`Preferences.Current->PreferencesView`) through `useAuthentication().createFrontEndClient` once the session is authenticated and exposes `{ values, definitions, status, error }`. `usePreference<T>(key)` returns `[value, setValue, { saving, error }]`; the setter calls `handlePreferencesInput` (`Preferences.Current->Save->PreferencesView`, `values: { [key]: value }`), shows the new value optimistically, updates from the reply and reverts with the error on failure. Without a stored value the declared default applies. `PreferencesView({ userName, userRole, children })` shows the user card, the theme switch (`granite.theme`, `light` or `dark`) and its `children` sections, which use `usePreference` for their own keys.

The server is the source of truth for the theme. The last theme is cached in `localStorage` key `granite.theme` (every access in try/catch) so the cached theme (default `dark`) applies at start-up and on the login page, and the server value replaces it once loaded. The Users screen shows value keys starting with `preferences.` or `granite.` read-only.
